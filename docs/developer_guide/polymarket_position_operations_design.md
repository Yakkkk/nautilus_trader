# Polymarket 持仓操作工程设计

状态：开发前设计。功能范围、成本口径和恢复边界已经确认；下文的数据结构名称和接入方式是拟实施的工程设计，不代表现有 API 已实现。

代码核查基线：`8dfef4b7725f`。本文与[现有集成指南](../integrations/polymarket.md)配合使用：集成指南描述当前能力，本文规定本次开发目标、必要改动和验收条件。

## 目标与范围

让框架受管的 split、merge、redeem 和 CTF convert 正确更新 Position、Cache、账户和 Portfolio，并在现有 CLOB 恢复能力的边界内恢复。
Backtest 和 Sandbox 仅增加 CTF convert。新增共享代码以这四类操作的接入为限，不建设通用链上操作或资产管理平台。

| Operation | Protocol | Live | Backtest | Sandbox |
| --------- | -------- | ---- | -------- | ------- |
| split     | CTF, V2  | ✓    | -        | -       |
| merge     | CTF, V2  | ✓    | -        | -       |
| redeem    | CTF, V2  | ✓    | -        | -       |
| convert   | CTF      | ✓    | ✓        | ✓       |
| convert   | V2       | -    | -        | -       |

CTF redeem 为全额双侧赎回，V2 redeem 指定 outcome 和数量。CTF convert 支持单 NO、多 NO。
V2 convert 及其 synthetic Other 适配本期不实现。

CTF convert 的输入仍限于未经济结算的可用 NO；输出可以包含已结算条件的 YES。
接收已结算 token 时保留其实际数量、归属与结算依据，按已知 payout 完成经济处理，相关市场保持不可交易。

Live 沿用 Deposit Wallet owner，账户为 Cash，OMS 为 NETTING，抵押币为 pUSD。
不新增 EOA、Proxy、Safe、session 签名、钱包部署、自动授权、自动链上赎回、跨协议迁移或 Combo 产品支持。
现有 CLOB 对其他钱包的支持不受此范围影响。市场协议 `v1` / `v2` 与 CLOB 服务版本 `2` 是不同概念。

convert 还要求 `negRisk=true`。同一网页事件不一定是负风险事件，不能从事件标题、市场数量或页面顺序推断转换资格。

## 接口与协议语义

### 受管命令

拟新增 `SubmitPositionOperation` 命令，经现有策略、RiskEngine、ExecutionEngine 和 ExecutionClient 路由。
复用命令 UUID 作为 `operation_id`，不再引入第二个请求身份。Rust 和 Python 暴露相同语义。

- `operation_id`：稳定的操作身份，用于关联、查询和去重。
- `trader_id`、`strategy_id`：请求发起者；不能据此覆盖实际被赎回份额的已有归属。
- `client_id`：按现有路由规则选择执行客户端和账户。
- `operation`：Split、Merge、Redeem、Convert 四类意图之一。
- `instrument_ids`：表达操作意图的 Instrument；数量和角色按下文验证。convert 仅携带选中的 NO 输入，完整影响范围由准备阶段解析。
- `quantity`：按操作定义提供；CTF 全额 redeem 不接受数量。
- `ts_init`：沿用 UnixNanos 时间戳约定。

拟新增按 operation_id 查询已知状态的最小入口。链上地址、calldata 和签名不由策略自行指定。
其他 adapter 的默认实现明确返回不支持，不能静默忽略新命令。新增 TradingCommand、ExecutionEvent 的路由分支必须全部覆盖。

风控遵循现有 TradingState：Active 下执行正常校验；Halted 拒绝新操作；Reducing 仅允许确实减少既有份额的 merge/redeem，
拒绝产生新 token 持仓的 split/convert。查询保持原有语义，不通过虚构订单价格将操作塞进订单限额计算。

- Split：提供同一二元条件的 YES/NO Instrument 和一份明确的正数 pUSD 金额。
  支出抵押币，收到两侧等量份额。
- Merge：提供同一条件的 YES/NO Instrument，每侧消耗同一明确正数数量。
  消耗完整份额，收到抵押币。
- CTF redeem：提供同一条件的两侧 Instrument，无 amount。赎回该条件下钱包两侧全部实际余额。
- V2 redeem：提供一个 outcome Instrument 和明确正数数量。消耗指定份额，取得实际 payout；零兑付合法。
- CTF convert：提供同一负风险事件的一种或多种 NO Instrument，每种消耗相同数量。
  收到未选中条件的 YES，可能收到净 pUSD。

不增加 `max` 数量、任意不等量 NO 自动拆单或无关操作批处理。保留既有低层 split、merge、redeem 接口；新增低层
`convert_positions(market_id, index_set, amount)`，最终命名遵循现有 Rust/Python 风格。

### CTF convert 的元数据与数量

使用现有 `NEG_RISK_CTF_COLLATERAL_ADAPTER`，地址为 `0xadA2005600Dec949baf300f4C6120000bDB6eAab`。
它调用 legacy NegRiskAdapter，并将收到的 USDC.e 包装成 pUSD 返还钱包；本功能不直接把 USDC.e 纳入账户。

设事件在转换时有 N 个链上已注册条件，选中 k 个 NO，每种输入为 a 个最小单位，转换费率为 feeBips：

```text
fee = floor(a * feeBips / 10000)
b = a - fee
每种未选中的 YES 输出 = b
预期 pUSD 返还 = (k - 1) * b
```

按合约整数运算处理费用，不先在浮点或四位行情价格上计算。k 可以为 1，也可以为 N；后者没有 YES 输出。
Live 的最终记账依据实际钱包效果，以上公式用于准备、核验和仿真，不能替代交易回执中的净收入。

准备阶段从输入 NO 定位真实 neg-risk market ID，通过只读 RPC 核实完整条件列表、费率、链上索引与 YES/NO token ID 映射。
选中 NO 对应 indexSet，其余全部条件的 YES 构成预期输出，包括已经结算的条件。
CTF 结算确定兑付比例，不删除 token 类型；NegRiskAdapter 按注册条件生成输出，不按交易状态过滤。
这些输出的身份和预期数量在签名前确定，执行后的回执用于核实实际效果。
Gamma event ID 不能充当链上 market ID；网页顺序或 token 数组顺序不能充当 indexSet。
全部预期输出必须能映射到现有 BinaryOption，缺少成员或映射时在签名前拒绝。
准备上下文保存此次使用的映射快照和目标账户的完整输入/输出 Instrument 集合，供屏障、操作记录及效果核验共同使用。

已知结算的输出还需保存权威 payout 及其来源，复用已有 InstrumentClose 和 CTF payout 核验路径。
停止交易、到期时间或缺少行情都不能单独作为零兑付依据；必要依据缺失或冲突时，签名前拒绝，已发送后则保留实际效果并继续核查。
已结算输出的非交易状态本身不构成拒绝理由，也不能据此省略映射、预期输出或回执核验。

显式数量必须为正数并精确到六位小数，拒绝隐式舍入、重复 NO、越界或空 indexSet、跨事件输入、YES 作为 NO 输入、未知协议和元数据冲突。
提交前按既有钱包路径验证 owner、canonical wallet、nonce、所需授权与余额；缺授权时不自动提交授权。
输入必须同时具有可核实的实物余额与可用账面多头份额，不能从账面空头或 provisional 数量构造可转换库存。
前序 CLOB 成交的确认来源与核心应用条件按下文并发准备流程核实；正常 WS `CONFIRMED` 不要求另取一份 REST 终态才能使用。

split 输出、merge/convert 输入及输出、V2 redeem 输入按请求策略解析已有 Position，沿用 NETTING 身份规则。
钱包中另一个策略持有同种 token，不意味着可以自动挪用其成本；本期不新增跨策略成本合并功能。
CTF 全额 redeem 因其固有的钱包级作用范围，按下一节处理各已有所有者。

split、convert 的 token 输出仅支持新建多头持仓周期，或并入同账户、同策略、同 Instrument 的已有多头。
准备阶段逐一检查全部输出目标；任一目标存在开放的策略账面空头时，签名前明确拒绝整笔操作，不等实际执行后再发现分录无法应用。
这一状态在现有 Cash/NETTING 下也可能出现：普通 CLOB Sell 使用账户级库存校验，共享钱包内其他策略持有 token 时，发起策略可能形成账面空头。
本期不改变普通 Sell 的行为，也不增加操作输出抵减空头及其成本分配语义。该限制按输出目标的当前开放持仓判断，不将另一策略的持仓或历史已关闭周期视为同一目标。
已结算 YES 输出继续按其结算依据接收和经济结算，不因这一接收限制而恢复对已结算输出的整体拒绝。

### CTF 全额 redeem 与归属

CTF redeem 的作用范围是钱包中的该条件，不是发起策略指定的一个 Position。
准备阶段核对两侧实际余额、已知开放持仓及已经济结算但尚未兑付的份额。

已知属于多个策略的份额分别保留原 Position、策略和成本归属；不新增“多策略一律拒绝”的规则，也不把整个钱包的收益归给发起策略。
多个策略不能作为整体未知归属的解决办法：若余额、份额来源或成本无法核实，不虚构分配，受管记账保持未解决状态。
发现提交前缺少必要映射时不签名；发现已执行交易证据不足时保留已知链上事实并继续定向核查。

已有 CLOB NETTING 对账会聚合账户数量，并对多策略归属发出警告；它不提供丢失历史后的精确策略归属恢复。
本功能保持这个边界。redeem 的操作记录区分发起者与各输入腿的实际所有者。

## 成本与收益

沿用平均成本，不引入 FIFO。数量、成本、费用及现金运算使用 Decimal 或现有领域类型。
实际成本累加值是权威，均价是派生值；不能用已经舍入的均价反复重建总成本。

### Split、卖出与 merge

- split 的投入成本由 YES、NO 各承担 50%，不产生已实现收益。
- 后续卖出按比例释放平均成本，收益为收入减释放成本、减当次佣金。
- merge 的净抵押币收入由 YES、NO 各分配 50%，各自确认分配收入减释放成本。
- 新收到的未结算份额新建多头持仓周期，或并入同账户、同策略、同 Instrument 的已有多头，按数量与总成本合并。

例：100 pUSD split 成 100 YES、100 NO，各承担成本 50。随后卖出 40 YES，价格 0.70，收入 28、释放成本 20，
当次手续费前收益为 8；剩余 YES 成本为 30，NO 成本仍为 50。

### Convert

令 C 为消耗 NO 的账面成本，R 为实际净返还抵押币。历史 CLOB 佣金已经费用化，不再加入 C。
先确定转入全部 YES 的总成本 K 和转换分配阶段的盈亏 P0，再处理输出自身的经济结算：

| YES output | Output cost K   | Conversion PnL P0 |
| ---------- | --------------- | ----------------- |
| Positive   | `max(C - R, 0)` | `max(R - C, 0)`   |
| None       | `0`             | `R - C`           |

仍有正数量 YES 时，K 按全部实际 YES 输出数量分配，已结算或零兑付的输出也参与分配。
没有正数量 YES 时，P0 包括亏损；所有 YES 都已结算仍属于有 token 输出，不能套用无输出分支。

转换费通过实际净输出体现，不另记一次相同费用。仍保留的成本进入剩余输出。
各输入 Position 的成本释放与转移必须显式记录，不能把成本转移当成一次全部亏损的平仓。
P0 按各输入耗用成本比例分配；总耗用成本为零时按耗用数量分配。

每个已结算输出按其实际数量 q、已分配成本 c 和权威单位兑付值 p，确认新增份额的结算盈亏 `q * p - c`。
这部分盈亏归属输出 Position，与输入上的 P0 分开记录；此次操作的已实现盈亏变化为两者之和。
零兑付输出承担的成本在此释放为损失，不能在分配时将其成本置零并转嫁给其余 YES。
经济结算本身不消耗链上 token。Live 的现金只反映实际抵押币变化，不能将 `q * p` 直接记为钱包已收到的 pUSD。
Backtest、Sandbox 则在既有模拟自动结算阶段处理相应现金，具体规则见后文仿真章节；成本分配与损益计算仍使用上述口径。

例：A/B/C/D 中消耗 100 NO A、100 NO B，账面成本分别为 80、70，无转换费。
收到 100 pUSD、100 YES C、100 YES D，两种 YES 均未结算。C=150、R=100，K=50，每种承担 25，P0=0。

如果 C=70、R=100 且还有未结算 YES 输出，K=0、P0=30。
如果全部 NO 转换后只收到 R=100，耗用成本 C=150，K=0、P0=-50。

若一次转换耗用成本为 6，无抵押币返还，实际收到两种各 10 股的 YES，其中一种已经按零兑付结算：
两种输出各分配成本 3，已结算输出确认损失 3，另一种保留成本 3。前者仍有 10 股实物 token，经济持仓数量和剩余成本均为零。

### Redeem 与经济结算

未经济结算的份额按实际兑付收入减释放成本确认收益。使用经核实的 payout 分配各 outcome 的收入，并验证合计与实际净 pUSD 一致，
不能将所有赎回默认按 1 兑付。

InstrumentClose 已经结算的份额不再确认一次收益。兑付只记录实际 token 消耗、兑付进度和账户刷新，
不重新打开 Position，不再次发出经济平仓事件，也不因追加兑付记录破坏当前经济结算标志。

从现有重放历史与操作记录导出各持仓周期已经济结算、尚未实际兑付的份额，保留 Position、周期和策略归属。
convert 在市场结算后新收到的 YES 形成独立可关联的接收与结算记录，不能并入旧周期重复结算，也不能因经济数量为零而丢弃。
多次接收、原有待兑付份额和后续 redeem 必须能按这些来源核对合计实物数量；仅查看当前 NETTING 周期不足以解释全部余额。
每个来源只扣除其后已核实的兑付消耗，结算前已经消耗的份额不能再次扣除。
沿用操作记录及持仓重放保存接收、结算和兑付关联，不建设独立应收资产账本。
若必要历史已被清除，就不能承诺恢复这些份额的精确策略归属。

反向顺序也必须成立：先 redeem 关闭经济持仓，后到的 InstrumentClose 不再结算同一份额。
保存经济结算与实际兑付的关联；不能用 Position.quantity 已为零推断钱包中已经没有待赎回 token。

### 精度与不变量

分配使用确定顺序：按 InstrumentId、PositionId 排序，普通腿按比例计算，最后一腿承担剩余值。
不提前量化成行情精度；保留现有 Money 舍入和子 Money 余数机制，完整记录每腿实际分配，最后减仓释放全部剩余成本。
成本均价可以为零，也可能因转换费资本化而高于 1；它不是一个可交易报价，不能套用 BinaryOption 的报价上下限校验。

必须满足：

- split 两侧成本之和等于投入成本。
- convert 分配阶段满足 `C + P0 = R + K`，包括没有 YES 输出的情形。
- 此次已结算输出的兑付价值合计为 Vs、此次未结算输出保留的成本为 Ku、转换及这些新增份额结算的合计已实现盈亏变化为 P 时，
  满足 `C + P = R + Vs + Ku`。
  Vs 是经济结算价值，与转换直接返还的 R 分开；Live 中对应实物仍待实际兑付，数量及其关联仍须保留。
  仿真的自动结算现金按后文规则体现，不改变转换分配阶段的成本守恒。
- 各腿盈亏之和等于操作总盈亏，尾差不能丢失。
- 所有资产最终卖出或兑付后，合计收益与净现金流及已计费用一致。
- 重复结果、查询和恢复不重复改变数量、现金或收益。

按 Instrument 分配的收益可能与 Polymarket UI 不同，这是约定口径的结果；不能据此覆盖本地成本。

## 核心接入设计

### 准备、提交与应用确认

```text
策略 -> RiskEngine -> ExecutionEngine -> PolymarketExecutionClient
                                         |
                        解析完整范围 -> ExecutionEngine 屏障确认
                                         |
                            成交终态与核心应用状态复核
                                         |
                      PositionClient 准备批次 -> Cache 记录确认
                                         |
                                  签名 -> Relayer
                                         |
                    已确认实际效果 -> ExecutionEngine 准备全部分录
                                         |
                       Position + Cache -> PositionEvent -> Portfolio
                                         |
                              应用确认 / 账户刷新请求
```

adapter 负责协议解析、签名、提交和将实际钱包效果归一化。核心负责完整范围的本地屏障，以及根据已有 Position 计算成本、应用变更并发出持仓事件。
提交采用准备确认流程：adapter 解析输入和预期输出后，将完整范围交给 ExecutionEngine 校验并建立屏障，收到成功确认才进入钱包批次准备。
这次内部交接沿用 operation_id，公共命令无需携带 adapter 推导出的输出。

PositionClient 复用现有钱包提交锁和签名实现，在锁内核实 owner、wallet 和 nonce，确定 deadline 及完整未签名批次。
这些字段均在签名前可得。提交任务通过可等待的内部请求，将准备上下文和批次交给 Cache 所属的执行线程序列化、保存，并取得明确的记录结果。
执行线程采用异步回复完成交接，提交任务等待回复时让出执行；受管 Live 路径使用节点配置的同一 Cache 后端。
独立的内存 recorder 只提供进程内记录，不能替代节点的持久化接入。

记录确认成功后，PositionClient 才签名并发送已记录的同一份批次；记录失败或尚未获得确认时不签名、不发送。
签名前若需要更改 nonce、deadline 或 calldata，必须重新准备并完成记录确认。
此时只保存提交意图与 nonce reservation，Position、现金和收益仍等待实际效果确认。
响应到达后补记 Relayer transaction ID，后续记录失败按恢复规则核查原提交，不通过再次签名发送来补救。

- 请求上下文：操作 ID、发起者、目标账户、操作参数、映射快照及完整输入/输出 Instrument 集合。
- 实际效果：token 输入/输出、净抵押币变化、协议、钱包、交易 hash、区块和回执定位信息。
- 准备后的分录：各 Position 的数量变化、释放/转入成本、盈亏变化、原归属和前置状态依据。
- 应用记录：各腿稳定身份、实际成本分配、应用结果、经济结算与兑付关联。

效果解析按 canonical 合约、目标钱包及 token ID 核实 TransferSingle/TransferBatch 和抵押币变化。
Router、adapter 的业务事件用于关联，不与实际转账各记一次。请求参数或 Relayer confirmed 本身不能证明每腿实际效果。
缺少交易 hash、回执、有效 payout 或完整效果时，不推导一个“预期成功”结果入账。
实际效果与准备范围不一致时保留证据并定向核查，不能丢弃范围外资产或直接套用旧分录。

核心先在临时状态中验证全部分录、精度、归属和前置状态，再在同一执行回调内替换内存状态，最后发布事件。
不在第一腿更新后才发现第二腿算术或映射失败。可以复用现有 Cache 替换和索引逻辑，必要时增加仅服务该用途的批量准备/提交入口。
对已结算 YES 输出，接收、成本分配、经济结算与实物关联属于同一批应用内容，完成后才能确认 Applied。
发布事件时 Cache 已包含完整结果，不向策略暴露可交易的中间持仓；其余未结算 YES 正常进入持仓及后续卖出流程。
可失败的算术、验证和序列化在内存替换前完成。持久化发送失败与内存已应用分别报告，不能通过重新应用来重试保存。
这里的内存一致性不等于数据库跨记录事务。
adapter 将结果发进队列不等于核心已经应用，必须接收核心的应用确认，再完成状态通知及屏障释放，模式与现有成交应用确认一致。

### 非订单 Position 与事件

采用明确的操作建仓来源，允许 opening_order_id 为空，并保存 opening_operation_id。
关闭时区分 closing_order_id 与 closing_operation_id。已有订单持仓的 ID、策略归属和 CLOB 填单路径继续沿用当前规则。
开仓来源在一个持仓周期中必须明确，不能同时声称由订单和操作建立。

PositionOpened、PositionChanged、PositionClosed 继续服务 Portfolio 和策略，但需增加触发操作的引用。
last_qty、last_px 对真实成交或 InstrumentClose 保留原值；纯操作事件允许这两个值为空，通过操作效果查询数量和成本变化。
不能给操作填一个虚假的成交价格，也不能用保留 ClientOrderId、伪造 OrderFilled 或创建虚拟 CLOB 订单规避模型改动。

该选择会涉及 Rust 类型、Python Optional 投影、PositionSnapshot、相关 Arrow schema 和消费者分支，属于本次必要的公共模型改动。
验收要求是旧订单持仓及旧序列化数据仍可读取，原 CLOB 事件仍提供原有非空数值；不是承诺所有 Rust 字段类型完全不变。
生成的 Python stubs 和 schema 相关产物从源定义及生成器更新，不手工编辑。

PositionReplayEvent 增加操作分录，并允许重放以操作建仓事件开始。
首次建仓、后续成交、操作减仓、再开仓、费用修订和 InstrumentClose 都须保持正确周期身份。
已结算输出复用非订单接收和结算机制，保留原权威结算依据，按先接收、后结算的顺序处理此次新增份额。
同一 NETTING PositionId 下的旧周期按现有快照规则保留，新增份额及损益有各自的操作和周期引用；不改写旧周期的数量、成本或已确认损益。
市场结果确定的时刻与新增份额确认的时刻分别保留，不能将结算后的接收回填到原结算时刻。
requires_replay_state 必须覆盖所有含操作历史的持仓，不能再只依赖 fill 数量或最后一个结算事件。

### 与 CLOB 并发的初期策略

屏障范围为目标账户的输入与预期输出 Instrument 的并集，跨该账户共享钱包的策略检查冲突，成本归属仍分别保留。
本设计仅做进程内协调，不增加账户级 token 预留系统；pUSD 刷新仍使用既有账户机制。
例如 A/B/C/D 事件中选中 NO A、NO B，屏障覆盖 NO A、NO B、YES C、YES D，其余 token 的普通交易保持原有行为。
全部 NO 被选中时没有 YES 输出，屏障只覆盖这些输入。
已结算或零兑付的 YES 输出也保留在完整范围内，不能因其无可交易敞口而提前移出屏障。

持仓操作准备分别核实前序 CLOB 成交的终态证据与核心应用状态。
通过既有证据校验且无冲突的 WS `CONFIRMED` 与 REST `CONFIRMED` 均可证明成交已确认，无需仅为更换证据来源重复查询 REST。
相关 fill 必须已经得到核心应用确认，缓冲中、等待应用或仅经 report 路由的记录不能作为已应用库存。
REST `FAILED` 对应的记录只有在必要的 void 已完成核心应用、或原本没有需撤销的 fill 时才算处理完成，失败份额不计入可用库存。
涉及已应用 fill 时，只有该 fill 的累计撤销量覆盖核心实际应用数量才算纠正完成；部分撤销仍保留未纠正库存并继续阻塞。
provisional、隔离、冲突、未知提交、待核查及 hard fault 仍按既有规则阻止相关操作，不能仅因 Position 数量已增加或订单已终态而放行。

定向 REST 核实用于现有结算机制确有缺口或矛盾的情形，例如断线遗留的 provisional 成交、未知提交及相互冲突的证据。
这些记录继续由既有定向核查路径处理，未解决时不签名发送；正常 WS 确认不依赖它们触发额外查询。

缓存成交事件恢复只证明 fill 已经应用，不能单独恢复其原 WS/REST 确认状态。
持仓操作准备涉及这类缺少终态的记录时，按目标账户和本次输入及预期输出范围，对已有可识别 venue trade ID 的记录触发现有定向 REST 核查。
入口预检与完整范围复检均覆盖这一补证动作；同一成交复用已有核查，不因重复请求启动并行查询，也不因仅恢复了核心事件而直接放行。
补证未完成时沿用现有未解决拒绝语义，不签名发送，并释放本次确定未发送操作的屏障；补证完成且必要 fill/void 应用已确认后，后续请求重新通过正常准备流程。
缺少可识别成交身份、查询失败或证据仍有冲突时继续阻止，不自动重提已拒绝的操作。
已经核心应用且完全撤销的成交不保留可用库存，因此不因 synthetic ID 无法查询而单独阻止后续操作；部分撤销仍保留未证明库存，按未解决状态继续阻止。
这是新操作准备时的按需补证，不要求启动时查询所有历史成交，也不增加历史搜索来源。

此处只调整持仓操作的准备条件，普通 CLOB Sell 沿用现有风控和提交检查，不新增前序成交必须取得 REST 终态的门槛。

1. adapter 完成输入/输出解析后申请完整屏障。元数据解析期间 CLOB 继续运行，因此取得屏障时重新检查状态，不能沿用解析开始时的检查结果。
1. ExecutionEngine 在同一执行回调内检查完整范围的已有屏障、活动订单、输入归属与数量，以及各输出目标的接收资格，并完成屏障安装。
   输出检查按目标账户和发起策略解析已有持仓，覆盖 split 两侧与 convert 全部预期 YES；任一检查失败均拒绝本次操作，不留下部分屏障，也不自动取消订单。
1. 屏障建立后阻止相关新的 submit/modify，并按上述规则复核完整范围内的未知提交、成交终态与核心应用状态。
   对恢复记录按需触发补证；已应用的 provisional fill 仍不可用，局部检查不能只依赖 ensure_resolved，也不能只认可 REST 来源。
1. 通过结算检查及状态版本复核后，进入前述记录、签名及发送流程；需要定向 REST 核实的记录须先解决。
   入口预检与屏障后的复检使用相同的终态口径，异步准备后仍须保证输入库存和输出接收资格有效；签名前若发现映射变化，重新解析范围并检查完整屏障。
1. 查询和必要的 cancel 保持可用，已经到达的成交及撤销不能丢弃；无关 Instrument 的 CLOB 交易继续执行。
1. 操作效果入账并得到应用确认后，按原准备范围释放屏障。确定尚未签名发送的拒绝也释放该范围；未知提交或待核实效果继续保留相关阻塞，钱包 nonce 协调仍沿用现有机制。

若晚到的权威成交、撤销或结算使前置状态失效，先按现有定向核查与重放处理，再决定是否能应用。
重放必须保留已执行的操作及其分配依据；若出现库存不足或相互矛盾的证据，保持该范围未解决，不能忽略操作、重复提交或强行凑平成本。
不承诺任何迟到修订都能全自动修复历史策略成本。

受管 split、merge 仍要求输入及输出尚未经济结算；convert 的 NO 输入也保持这一限制。
convert 的 YES 输出按其实际结算状态分别处理：未结算份额正常建仓，已结算份额按前述规则接收并完成经济结算。
已结算输出所属市场保持不可交易，屏障释放或操作 Applied 均不改变这一状态。
若操作等待期间收到 InstrumentClose，协调其与操作效果的处理顺序，先核实实际执行范围，再对尚未结算的经济份额结算一次。
已知结算后新增的输出同样使用权威结算依据，仅处理本次新增份额；重复或晚到的 close 不得再次结算旧份额或新增份额。
需要暂缓相关经济结算事件时只影响该操作范围，不停掉行情或无关 Instrument 的结算。
redeem 同时覆盖未经济结算和已经济结算的份额，按前文规则区分收益确认与实物兑付。独立低层客户端仍保留既有调用语义。

这些是控制初期复杂度的工程选择，不将普通 CLOB 全部改为等待链上最终确认。
外部钱包工具和其他进程不受本地屏障控制，仍保持现有单协调提交进程的使用边界。

### 账户与 Portfolio

Live 的 pUSD total 仍以 venue 报告为准。成功应用后刷新受影响 token 与抵押币的 CLOB 余额缓存，再通过现有账户刷新路径发布 AccountState。
保留 BUY 订单预留、unsettled spend、陈旧响应与 reconnect/reset 处理；不能通过持仓操作事件再加减一遍 Live total。
刷新失败时重试读取和刷新，不重提链上操作，也不撤销已核实的 token 效果。

Portfolio 继续消费 PositionEvent 与 AccountState，重算数量、成本、已实现及未实现收益。
已结算输出完成经济结算后不保留开放敞口，按权威 payout 确认相应损益，不等待交易行情为其估值。
未结算持仓缺行情时仍遵循现有 pending calculation 行为，不能把缺失价格当作零；接收零兑付 token 不增加 pUSD 余额。
新增操作不得向 CLOB 成交报表写入成交量或伪造费用。

## 持久化与恢复

### 最小操作记录

使用现有 Cache general bytes 和后端，不新增独立 WAL。记录有明确 schema_version，以操作 ID 定位，并保存恢复所需索引。

- 发起者、账户、钱包、协议、操作、条件/事件、输入输出映射快照、数量及完整屏障范围；保留它们与原命令输入的区别。
- 签名前确定的链 ID、完整有序批次的 target/value/calldata、nonce、deadline 和恢复查询范围；不保存签名或凭据。
- 可获得的 Relayer transaction ID、链上 hash、实际效果和证据定位。
- 分离的 venue 状态与本地应用状态、各腿分配/应用身份、已结算输出的 payout 依据及接收、结算和兑付关联。

按前述准备流程在签名前写入意图、完整范围和 nonce reservation，再随响应、效果和应用确认更新。
Cache.add 返回成功只说明现有持久化入口接受了写入，不等于数据已经可靠落盘。
不为这份记录声明比当前 CLOB 更强的同步刷盘或每个崩溃点无损恢复能力。

### 保存与加载 Position

Redis、SQL 的 add_position 不能继续要求无条件取得 last OrderFilled 后才保存快照。
操作起始持仓使用完整 replay_state，并建立正常的 Position、OMS 和打开/关闭索引；复用 add_position_without_order 的意图，
但补齐其当前仍依赖 opening fill 的下游行为。

loader 必须能发现只有重放快照、没有首笔成交列表的持仓，不能只增加快照写入而保留“从成交列表发现 Position”的读取假设。
SQL 表和 Arrow 字段中非空订单引用需同步评估并通过正常 schema/migration 机制调整。
旧 fill-only 数据和旧快照仍走兼容读取；新操作记录未知版本应给出明确错误，不能按空持仓忽略。

各腿以 operation_id 和稳定腿身份去重，应用标记只有在内存全部应用成功后更新。
腿身份由操作、账户、Instrument、Position/周期和方向确定，不使用轮询时间。
已结算输出的接收与其经济结算结果分别核对，并由同一输出腿及周期关联；不能仅以市场已有 close 或输出腿已保存认定处理完成。
重复使用同一市场的结算依据不代表新增份额已经处理过，去重必须能区分不同操作的接收。
链上效果另以链 ID、交易 hash、钱包及 log/batch-item 定位去重，防止同一回执经重复查询、解析或不同操作 ID 再次入账。
重启时比对操作记录、各 Position 重放标记及快照，不仅检查一个 APPLIED 布尔值。
部分记录缺失或互相冲突时定向核实；证据不足则保留未解决状态，不声称多记录写入具备 ACID 或跨进程 exactly-once。

### 状态与恢复处理

venue 状态与应用状态分开。Relayer confirmed、链上效果完整、核心已应用和账户已刷新是不同事实。

- 签名前校验失败：明确拒绝，无链上提交，也无待恢复提交。
- 已准备并可能发送，但未取得 transaction ID：标记 UNKNOWN，保留意图、完整屏障与 nonce reservation。
  重启后核查现有可用证据；无法核实原交易身份及实际效果时保持 UNKNOWN。
- 已取得 ID，仍在等待：保留原 ID，不重提。重启后自动查询原交易。
- confirmed，但效果不完整：保留 confirmed 事实，应用待核实。重启后继续取得回执及实际效果。
- 效果完整，尚未应用：准备并核验全部分录。重启后比对各腿应用状态，避免重复应用。
- 已应用，账户刷新未完成：保留持仓效果。重启后恢复持仓并刷新账户，不重复现金变化。
- failed / invalid 或冲突：不据状态名称猜测旧签名已经失效。重启后按原有 nonce、终态及未知提交规则核实。
- Cache 丢失：无精确本地历史。重启后仅按现有 CLOB 能力重建敞口，不保证历史成本和策略归属。

恢复使用已保存的操作记录、Cache、Position 重放状态，以及通过已知交易身份取得的 Relayer 查询结果和链上回执。
无 transaction ID 但已有可验证交易证据时，仍通过相同的核心核对入口处理。
本期不新增钱包活动查询、按时间窗口搜索候选交易或 `eth_getLogs` 搜索接口，也不建设全链历史索引。

仅有准备记录不能证明未发送：进程可能在签名、发送或补记响应之间退出。
nonce 推进、余额变化和经过的时间也不能单独证明原操作已执行。缺少可验证证据时保持 UNKNOWN、相关屏障及 nonce reservation。
wait 超时不取消签名、不缩短其 deadline。保留未知 reservation，不以本地经过一段时间为重试依据。

### 启动对账

先加载操作记录和 Position 重放状态，按保存的账户及完整输入/输出范围恢复屏障，并核查已知待确认操作，再对受影响范围运行普通 CLOB 持仓对账。
避免先根据数量差合成一笔普通成交，随后再应用同一转换。
在接纳新的钱包操作前，将保留的 nonce reservation 恢复到现有钱包协调状态；reconnect、stop/start 或 Live reset 不能被用来绕过未知签名。
没有持久化证据时仍采用已确认的降级边界，不声称独立客户端或其他进程会自动获得丢失的上下文。

普通 CLOB 成交从缓存恢复后，核心应用事实与成交终态证据仍分别处理；一般对账报告不能替代对原成交的完整终态核查。
仅恢复缓存不触发全量历史成交查询。后续持仓操作需要这些库存时，按准备流程对相关输入及输出范围补证；补证前的普通 Sell 仍沿用现有风控和提交规则。
该流程不改变下述已提交持仓操作的自动核查与安全应用要求，也不将已拒绝的新操作加入自动重提队列。

恢复任务对有 transaction ID 的待确认操作自动查询原交易，取得完整实际效果后交给引擎统一核对。
核对以 operation_id 和稳定腿身份关联操作记录与 Position 重放历史，并验证持仓周期、数量、成本及收益分配；直接重发 Confirmed 结果不能代替该检查。

重放历史已包含全部预期腿且内容一致时，恢复任务只补齐操作记录和账户刷新，不重复改变持仓或发布持仓变更事件。
含已结算输出时，完整应用还包括该次接收对应的经济结算及实物关联；已保存接收但缺少后续处理不能直接视为 Applied。
补齐时沿用原数量、分配成本、payout 和周期身份，不重复接收 token，不重复确认结算损益。
尚未应用任何腿时，确认原分配依据与前置状态完整后，通过正常应用路径完成记账。
若仅保存了部分腿，或记录与 Position 状态冲突，先定向核实；能够还原一致的原分配与状态时才补齐，否则保留未解决状态及相关阻塞。
这些判断不能仅依据操作记录的 APPLIED 标志，也不能用重启后的平均成本重新计算原操作。
自动查询、重复结果和再次重启均服从同一核对规则；恢复记录和屏障只是恢复流程的起点。

对于有本地操作成本依据的 Instrument/account 报告，复用 AvgPxReconciliation::OpeningOnly：
保留本地平均成本，继续校验数量，允许分配造成的均价差异与零成本持仓。
不全局取消均价校验，不用 Data API 均价覆盖已保存的操作分配。
缺失的 Data API 余额记录仍不作为归零证据，scope、精度和 dust 容差沿用当前 CLOB。

对已经济结算的 convert 输出，经济数量为零与钱包仍持有 token 可以同时成立。
核对实际余额时使用保留的接收、结算和兑付关联解释这些份额，不能将其重新合成为普通 CLOB 开仓，也不能只凭经济数量为零清除实物记录。

## Backtest 与 Sandbox

只接入 CTF convert。split、merge、redeem、V2 convert 在这两个环境中明确返回不支持，不通过组合虚拟成交模拟。
账户与持仓范围为 Polymarket 的 Cash/NETTING；不增加 Margin/HEDGING 转换语义。

调用方在运行前通过现有 Instrument/Cache 元数据入口显式预置 `neg_risk_market`，包含完整事件成员、真实条件索引、YES/NO ID、费率和有效时间。
测试 fixture 使用同一入口，不增加测试专用接口。Gamma 事件顺序不能充当链上 question index；Polymarket 数据 provider 本期不增加链上元数据自动补全。

数据准备阶段可使用链上只读信息制作元数据快照，历史回测采用对应时点的快照。
元数据缺失、冲突、跨事件或时间不适用时拒绝，不在回测运行时联网读取当前状态代替历史状态。

共享合约数量/费用算法及核心成本/效果应用逻辑，分别从 Live 回执或仿真计算取得效果。
仿真同样保留完整事件中的已结算 YES 输出，并复用核心的成本分配与经济结算规则。
对应 Instrument、权威结算数据及其有效时点由调用方通过现有入口预置；输出已结算且依据完整时不因不可交易而拒绝。
输出目标已有策略账面空头时，与 Live 使用同一接收限制，在仿真效果应用前明确拒绝，不产生部分持仓或现金变化。
输入可用性、未解释的非活动状态及缺失映射仍须验证，不以当前链上状态或未来结算结果填补历史数据。
已确认但核心尚未应用的转换输入按操作保留，后续转换、普通卖出及改单在重新校验可用数量时扣除这些待应用份额，不得让两个请求同时消耗同一批库存；转换校验同时计入撮合侧已产生但核心尚未应用的成交。核心应用后释放保留。
转换等待应用期间收到输入结算时，先应用转换再结算剩余库存；撮合侧到期结算跳过被保留的持仓并保留收到的权威 close，待转换应用并释放保留后按该 close 补结算，普通 CLOB 成交的结算顺序不变。

正常到期清理须考虑完整事件的转换输出依赖。
已结算 YES 仍可能是其他有效 NO 的转换输出，经济持仓为零或撮合引擎退役不能单独作为释放定义和结算资料的依据。
只要本次运行已预置的事件仍可能发生受支持的转换，或尚有待处理转换引用这些资料，框架就须保证对应 Instrument 定义和权威结算依据可用于完整输出解析与应用。
撮合引擎和行情状态继续按既有规则清理；必要资料可保留或通过现有运行内机制重新提供，不要求固定存放位置。
确认事件已无可能成为有效输入的 NO，且没有待处理转换依赖后，相关保留状态可随既有清理释放。
调用方未提供或主动清除必要资料时仍按缺失证据拒绝；上述协调仅覆盖正常自动清理，不增加 provider 补全、联网查询或历史恢复来源。

仿真现金通过现有 CashAccount 和 AccountState 机制更新，与 Live 的 venue total 路径分开。
convert 直接返还的抵押币 R 与已结算输出的模拟自动结算收入分别核算；后者按实际收到的数量 q 与已生效的权威兑付值 p 计为 `q * p`。
成本只影响已实现收益，不从这笔兑付现金中再次扣减；零兑付输出不产生该项现金收入。
每次新增输出份额在对应持仓效果安全应用后，按既有模拟到期结算语义产生一次现金收入，并与后续普通到期处理协调结算归属。
重复结果、重复 close 或再次查询不重复计入同一份额；frozen_account 对直接返还和自动结算收入均保持原有行为。
未结算输出仍在其后满足结算条件时走既有仿真路径，不在 convert 时预记未来兑付。
这不引入独立的模拟 Redeem 命令或链上 token 消耗模拟，Live 仍等待真实抵押币变化后刷新账户。

Sandbox 复用其现有 exchange、命令队列和延迟模型，Backtest 复用模拟时钟和队列，不另建区块、gas、Relayer 或链上失败模拟系统。
重置时清除本次操作的队列、记录、去重及转换依赖保留状态，对 Instrument 和 Cache 的处理仍服从现有 reset 语义。

## 测试与验收

测试层次与 CLOB 保持一致。共享数学在一个层次充分验证，节点和 Python 使用少量代表性用例，不机械复制整个 Rust 矩阵。
既有 wallet、签名、nonce、错误处理测试继续复用。mock 测试不依赖 adapter 环境变量。
真实事件和回执样例固化为 fixture，不在测试运行时依赖公网当前状态。

- 协议单元：放在 polymarket positions/calldata、amounts、效果解析模块。
  验证 ABI、整数费用、ID、索引、输入校验及回执归一化。
- 模型与核心：放在 model Position、execution、common Cache、portfolio 对应测试。
  验证非订单建仓、成本转移、事件来源、重放及整体内存应用。
- 成交结算边界：扩展现有 settlement registry 测试，区分终态证据来源与核心应用状态。
  验证 WS/REST 确认后的可用性、provisional 与未完成应用的阻塞、失败成交的累计撤销覆盖要求，以及恢复记录按操作范围补证，不在各层复制状态矩阵。
- 底层集成：扩展 `crates/adapters/polymarket/tests/integration/positions.rs`，
  复用 Deposit Wallet mock，增加 convert 与必要 receipt/payout 情况。
- Live 集成：扩展 `crates/adapters/polymarket/tests/integration/live.rs`，
  验证策略/执行路由到持仓、缓存、账户和 Portfolio。
- Node：扩展 `crates/adapters/polymarket/tests/integration/node.rs`，
  仅增加少量生产 factory/node 接线及状态回传用例。
- 持久化：扩展 infrastructure 现有 Redis、Postgres cache 测试，
  验证无 opening fill 的保存与读回、旧数据兼容和操作去重标记。
- 仿真：扩展 backtest integration、sandbox integration/execution，
  仅验证 CTF convert 的现金、时序、元数据、已结算输出、正常清理后的输出依赖、reset 与 frozen_account。
- Python：沿用既有 PyO3/adapter 接口测试模式，验证 Decimal、Optional 来源字段、错误与生成投影。

以下是验收场景，不要求建立新的用例管理框架：

- 单 NO、部分多 NO、全部 NO：输入、各 YES 输出及现金与合约语义一致。
- 完整事件含已结算条件：准备和回执解析均保留其 YES 输出，不按市场交易状态或零兑付过滤。
- 仅含 NO 的命令：签名前解析完整 YES 输出；输入或输出侧已有活动订单时拒绝，共享钱包的其他策略也纳入相关冲突检查，无关 token 可继续交易。
- 记录失败或等待确认：确认前不签名发送、不改变持仓和现金；确认后发送的批次与记录一致，缺少响应时不重提。
- 非零费用、最小单位、尾差：整数扣费正确，数量和总成本不丢失。
- C 小于 R、C 等于 R、零成本、成本均价大于 1、无 YES 输出：P0 与输出成本符合公式，不误用报价上下限。
- split 后仅卖出 YES：NO 成本不被错误释放，卖出收益正确。
- 买入两侧后 merge：各侧释放成本及合计收益正确。
- 未结算输出并入已有多头：使用原总成本加输出成本得到新平均成本。
- 输出目标已有策略账面空头：通过现有 Cash/NETTING 普通 Sell 构造可达状态，convert 在签名前拒绝，Relayer 提交计数为零，
  输入输出持仓及成本、现金和 Portfolio 不变，不残留本次操作屏障。共享核心覆盖 split 同源限制，Backtest/Sandbox 各保留少量同入口拒绝用例，不复制完整矩阵。
  同账户其他策略的持仓不被挪用或改写；普通 Sell 保持原有行为，正常多头追加和历史关闭周期后的接收继续成功。
- 未结算与零兑付 YES 混合输出：全部实际输出参与成本分配；零兑付部分确认相应损失并保留实物数量，其余 YES 正常建仓。
  检查 Cache、PositionEvent 与 Portfolio 的完整结果，已结算市场保持不可交易，零兑付部分不产生现金收入。
- 已知非零 payout、全部 YES 输出已结算：按权威兑付值确认经济损益，仍使用有 YES 输出的分配分支。
  Live 保留待实际兑付的实物，现金只反映真实抵押币变化；仿真按既有自动结算机制更新现金。
- 同一已结算 YES 原有待兑付份额及多次新增输出：各周期数量、策略与损益保持独立，后续 redeem 正确关联全部实际消耗而不重复结算。
- CTF 双侧/多策略全额 redeem、V2 部分 redeem：实际消耗、payout 与各已有归属正确。
- Live 的 InstrumentClose 与 redeem 的两种顺序：经济收益和平仓事件各确认一次，现金只实际兑付一次。
- Live 买入、convert、卖出、重启：首次 Convert 准备时，前序成交仅经正常 WS `CONFIRMED` 且已完成核心应用、相关订单终态，
  不预置成交 REST 终态，终态判断也不依赖额外成交 REST 查询。操作仍需正常提交并核实实际效果，后续卖出和恢复的数量、成本、收益与身份一致。
- 重启后使用已有 CLOB 库存：通过正常成交和缓存重放恢复持仓及终态订单，不直接预置 registry 终态；首次相关持仓操作请求触发定向补证，补证前拒绝且不提交。
  核查确认并完成核心应用后，重新申请可正常应用且只提交一次；REST 失败涉及原 fill 时，必须使每条 fill 的累计撤销量覆盖核心实际应用数量，失败份额不能成为可用输入，部分撤销仍阻塞。
  同时覆盖输入侧及已解析输出侧的恢复记录：仅查询本次完整范围内已知成交，重复请求复用核查，无关历史不查询；缺身份或证据不足时不发送、不残留未发送操作屏障。
  保留普通 Sell 对照与“仅恢复缓存不全量补查”的既有测试，不通过全局放行恢复成交或扩大启动扫描范围满足验收。
- 终态与应用状态组合：WS/REST `CONFIRMED` 已应用时通过局部结算检查，provisional 已应用时仍阻止；
  已确认但 fill 尚在缓冲、等待应用或仅经 report 路由时继续阻止。REST `FAILED` 尚待 void 应用或仅部分撤销时阻止，累计撤销覆盖核心实际应用数量后失败份额不成为库存。
  输入与输出均纳入复检，准备期间出现的冲突或待核查状态不能被入口检查结果覆盖。
- 普通 Sell 回归：无相关操作屏障或其他既有阻塞时，不因前序成交缺少 REST 终态而拒绝；沿用原有提交与风控行为，不复制整套 Convert 矩阵。
- provisional、fill void、晚到修订、同时到达结算：操作屏障和重放正确，冲突不被伪造分录掩盖。
  convert 输出的 close 先到、等待期间到达或应用后到达时，均只结算相应经济份额一次；未知 payout 不默认按零处理。
- 重复效果、重复轮询、重启后重放：每腿不重复增减，账户不重复计现金。
- 有 ID 待确认、缺回执：重启后自动查询原交易、核实实际效果并安全应用，提交请求计数不因恢复增加。
- 无 ID 且缺少可验证证据：保持 UNKNOWN、完整屏障及 nonce reservation，不发起候选交易搜索，也不重签重提。
- Position 已保存而操作记录未更新：通过逐腿核对补记，重复查询和再次重启不重复改变数量、成本、收益或发布持仓变更事件。
- 已结算输出的接收已保存而结算关联不完整：有原始分配依据时安全补齐，否则保持未解决；重复核查不重收 token、不重复确认损益。
- 完整范围的保存与恢复：从操作记录恢复包含 YES 输出的屏障，按同一范围释放，未知结果不提前解除阻塞。
- 只保留操作起始快照、部分标记不一致：能加载无 fill 持仓，冲突不直接当作完整 APPLIED。
- 本地均价不同于 venue、零成本：相关 OPENING_ONLY 数量对账可完成，其他检查未被放宽。
- 非负风险事件、V2 convert、缺输出映射：签名前明确拒绝，缓存、仓位和现金不变。
- 调用方预置仿真元数据：正常入口可执行 convert，缺失、冲突或过期时拒绝；延迟执行与 reset 按现有时序处理，不联网补全、不产生残留操作。
- 仿真自动结算现金：Backtest、Sandbox 各覆盖零兑付和正兑付的少量代表场景，通过真实执行、账户、Cache 和 Portfolio 核对数量、成本、收益与现金，不复制完整核心矩阵。
  例如转换前现金为 1000、消耗 NO 成本为 50，无直接抵押币返还，收到 99 股按 1 兑付的已结算 YES 时，现金为 1099，此次已实现收益为 49。
  重复结果及重复 close 不重复结算，frozen_account 保持既有余额行为；不能只核对 Position 关闭或已实现收益。
- Sandbox 正常清理后转换：完整事件与权威结算事实已按约定提供，部分 YES 输出正常到期清理后，另一 NO 仍具备有效输入资格且库存充足时，转换仍能完整应用。
  与未触发清理的场景对照，验证已结算输出关闭、未结算输出正常建仓，并检查不再被转换依赖的普通到期清理和 reset 仍符合既有语义。
  验收依据是转换结果与状态正确，不将内部资料必须被删除或必须存放在某个缓存中作为断言。

拒绝用例按输入与输出角色区分：保留已结算 NO 输入、缺失映射和 payout 依据冲突的校验；
已结算 YES 输出改为验证完整接收与结算，不能仅根据输出结算状态断言整笔拒绝。

重启测试沿用 live.rs 的 seeded cache 模式，并增加确实涉及序列化的后端读回测试。
不为本功能新增全崩溃点故障注入平台、性能测试平台或真实资金交易前置要求。
实现后运行受影响的模型、执行、Cache、Portfolio、adapter、仿真和 Python 测试，以及仓库规定的格式与 pre-commit 检查。

完成条件是上面的支持矩阵、成本不变量和恢复场景均有对应实现及测试证据。
阶段原型不能被描述为完整功能已交付，独立客户端提交成功也不能替代框架状态更新验收。

## 可行性与评审关注

CTF 多 NO 的底层调用已有部署合约支持，现有客户端也提供签名、nonce 协调和 Relayer 基础；无需新合约或新抵押币体系。
框架已有精确成本、持仓事件、Cache、重放快照和均价对账机制，可以在其上完成必要扩展。
工作会横跨共享模型、执行、持久化和仿真，不能只修改 adapter 数量后宣称完成。

已结算 YES 输出可复用非订单接收与 InstrumentClose 的经济结算能力，无需新增合约或独立资产账本。
Live 沿用显式 redeem 与账户刷新，不增加自动链上赎回；仿真衔接既有模拟到期现金处理。
必要改动是将输出接收、成本分配及对应结算作为完整应用处理，补齐跨周期实物关联和恢复核对，并区分输入库存校验与输出接收资格。
仅移除已结算输出的拒绝条件仍会留下开放持仓、待兑付数量丢失或恢复重复记账风险，不能作为完成依据。

业务口径已经确定。实现评审重点是以下工程选择是否被完整落实：

- 非订单来源、nullable 订单/成交字段与旧 Rust/Python/Arrow 消费者的兼容改动。
- 操作起始持仓在两个后端的发现、加载和完整重放。
- 恢复 CLOB 库存在持仓操作准备时按需补齐终态证据，复用既有定向核查，不改变普通 Sell 或启动历史查询范围。
- split/convert 输出接收资格在发送前验证，拒绝策略账面空头目标，避免链上成功后才发现本地分录不可应用。
- 初期相关活动订单拒绝策略及 InstrumentClose 交错处理，避免不受控并发扩大实现规模。
- CTF 全额 redeem 的多策略归属与已经济结算份额的实际兑付。
- convert 已结算输出的完整接收、经济结算、跨周期实物关联与幂等恢复。
- 仿真自动结算现金、转换输出资料的保留期与正常清理/reset 的一致性。
- 异步持久化和证据不足时保持未解决状态，不扩张恢复承诺。
